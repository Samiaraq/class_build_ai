# How Mini ClassBuild Works

This document explains the main technical mechanisms behind Mini ClassBuild: prompts and retries, PDF processing, chunking, embeddings, retrieval, citations, validation, and the saved-course format.

## 1. Prompts and Structured Output

Mini ClassBuild uses the Groq API to generate course outlines, lesson content, and quizzes.

The application sends structured prompts that describe the requested content and its constraints. For example, lesson generation includes the selected lesson's number, title, description, and learning objectives.

The application requests JSON responses and validates them using Pydantic models. This keeps generated content consistent with the application's expected structure.

The `request_structured_json()` function handles invalid JSON responses:

- It allows up to two structured-generation attempts.
- If the first response contains invalid JSON, a second attempt uses a retry prompt.
- Groq client errors are raised instead of being treated as invalid JSON.

The Groq SDK also has its own retry mechanism for temporary failures. The `GROQ_MAX_RETRIES` setting controls the number of SDK retries:

- Default: 1 retry.
- Maximum allowed: 3 retries.
- Invalid values fall back to the default, and values are clamped to the allowed range.

The two retry layers are bounded to prevent unlimited requests. API keys are also redacted from error messages before they are exposed.

## 2. PDF Processing and Chunking

PDF processing is handled by `classbuild/rag/pdf_processor.py`.

The processing pipeline works as follows:

1. Validate the uploaded file.
2. Extract text from each page using `pypdf`.
3. Clean the extracted text.
4. Split each page into smaller overlapping passages called chunks.
5. Build a `ProcessedDocument` containing the document information and chunks.

The application accepts PDF files up to 10 MB. It checks the file extension, size, content, and PDF header.

Text cleaning normalizes Unicode, standardizes line breaks, removes control characters, and reduces repeated spaces.

The chunker uses these default settings:

- Chunk size: 800 characters.
- Chunk overlap: 150 characters.

Chunks are created separately for each page, so a chunk never spans two pages. The chunker prefers paragraph breaks and sentence endings when choosing where to split the text.

The overlap helps preserve context around chunk boundaries. Each chunk receives an identifier that includes its page and position, such as `p3-c2`.

The application does not perform OCR. Pages without extractable text remain empty.

## 3. Embeddings and Semantic Search

Mini ClassBuild uses the local embedding model `sentence-transformers/all-MiniLM-L6-v2`.

An embedding converts text into a numerical vector representing its semantic meaning. The model produces vectors with 384 dimensions.

The model runs on the CPU and is loaded once per process. The first use downloads the model; later uses can load it from the local cache.

The `EmbeddingService` provides two main operations:

- `embed_texts()` converts multiple passages into vectors in batches.
- `embed_query()` converts a search query into one vector.

The retriever uses cosine similarity to compare the query vector with the document's chunk vectors.

The search process returns the three highest-ranked passages by default. Results are sorted by similarity, with the original document order preserved when scores are equal.

The embedding index is cached for the loaded PDF. This avoids embedding all passages again for every search or generation request.

The index is associated with the document fingerprint, chunk IDs, and embedding model name. It is rebuilt when these no longer match the current document.

## 4. PDF-Grounded Lessons and Citations

When the user chooses to use an uploaded PDF as a reference, the application retrieves relevant passages before generating a lesson.

The retrieval query combines the course title with the selected lesson's title, description, and learning objectives.

The grounded lesson generator:

1. Retrieves the top three passages.
2. Keeps passages with a similarity score of at least 0.30.
3. Stops if no passage meets the threshold.
4. Sends the retrieved passages and their allowed IDs to Groq.
5. Checks whether the generated lesson uses the retrieved evidence.
6. Validates the lesson and its citations.

The prompt instructs the model to use the supplied passages, cite their exact IDs, avoid inventing source IDs or page numbers, and treat PDF text as untrusted input.

The model chooses which retrieved passage IDs each section cites. However, source details such as page number, filename, text, and similarity score are copied from the retrieval results, not generated by the model.

If the evidence is relevant but the draft contains no citations, the generator can request one regeneration with an additional citation instruction.

Pydantic validation checks that:

- A grounded lesson contains citations.
- Every cited ID exists in the source list.
- Every listed source is cited.
- Duplicate sources are rejected.
- Sources belong to the expected PDF fingerprint.
- Source details match the actual retrieved passages.

The application also checks page numbers mentioned in lesson text. A lesson is rejected if it mentions a page that is not among its cited pages.

Ordinary lessons generated without a PDF do not contain source citations.

## 6. Validation

Pydantic models validate the data returned by the AI before it is accepted by the application.

Course outline validation checks required fields, non-empty text, difficulty, learning objective counts, lesson numbering, unique lesson titles, and whether the result matches the requested lesson count and difficulty.

Lesson validation checks the lesson structure, selected lesson number and title, section count, exercise count, and citation consistency when the lesson is PDF-grounded.

Quiz validation checks that each quiz contains exactly five questions, each question has four distinct options, correct-answer indexes are valid integers, questions are not repeated, and the quiz belongs to the selected lesson.

Structured-output validation also rejects invalid JSON and limits the number of generation attempts.

These checks prevent malformed, incomplete, or inconsistent AI responses from being accepted as valid course content.

## 7. Saved-Course Format

Mini ClassBuild saves courses as JSON files on the user's local computer. It does not use a database or a network service for course storage.

Each saved course is represented by the `SavedCourse` model and includes:

- `schema_version`: the saved-file format version.
- `app`: the application name.
- `course_id`: a unique random identifier.
- `created_at` and `updated_at`: timestamps.
- `topic` and `difficulty`.
- `outline`: the validated course outline.
- `lessons`: generated lesson content.
- `quizzes`: generated quizzes.
- `source_document`: the PDF filename and fingerprint, when applicable.
- `selected_lesson`: the last selected lesson.

Files use the naming pattern `course-<id>.json`. The ID is a random 32-character hexadecimal value and is not derived from the course title. This allows different courses with identical titles to be saved separately.

The saved-course model checks consistency between the outline, lessons, quizzes, PDF references, and selected lesson.

The store validates course data both when saving and when loading it. It also checks the schema version, file size, and whether the filename matches the ID stored inside the file.

Writes are atomic: the application writes to a temporary file and then replaces the target file. This helps prevent partially written course files if an operation fails.

The saved format intentionally excludes:

- API keys.
- Lesson-chat conversations.
- Quiz answers and attempts.
- The original PDF file.
- Embedding vectors.

For PDF-based courses, only the source filename and fingerprint are saved. After loading such a course, its existing lesson content and citations remain available, but PDF-based generation and PDF answers stay disabled until the original PDF is uploaded again and its fingerprint matches.

The `schema_version` field allows future versions of the application to detect older saved formats instead of interpreting them incorrectly.
